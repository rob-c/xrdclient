# S3 object storage

Analysis facilities increasingly keep data in a bucket rather than in a
namespace, and the same three entry points reach one: `s3://bucket/key`
dispatches to an S3 filesystem the way `davs://` dispatches to WebDAV.

```python
with xrdclient.open("s3://my-bucket/store/f.root", "rb") as fh:
    header = fh.read(1024)

fs = xrdclient.FileSystem("s3://my-bucket")
for entry in fs.scandir("/store"):
    print(entry.name, entry.stat.st_size)

xrdclient.copy("root://eos.example.org//store/f.root", "s3://my-bucket/store/f.root")
```

Nothing here needs a wheel either: the requests are `http.client`, the
listings are `xml.etree`, and the signature is `hmac` and `hashlib`. There is
no `boto3` in the dependency tree and none in the import graph.

## Credentials

They are found the way every other S3 client finds them, in this order:

1. `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, with the optional
   `AWS_SESSION_TOKEN` for a temporary credential.
2. `~/.aws/credentials` (or `$AWS_SHARED_CREDENTIALS_FILE`), the profile named
   by `$AWS_PROFILE` or `default`.

```python
from xrdclient.s3 import Credentials, S3FileSystem

fs = S3FileSystem("s3://my-bucket", credentials=Credentials(key, secret))
fs = S3FileSystem("s3://my-bucket", credentials=None)   # a public bucket
```

`credentials=None` signs nothing, which is what an anonymous read of a public
bucket wants. `Credentials.discover()` is the search above, and returns
`None` when it finds nothing rather than inventing an empty key.

A `Credentials` never prints its secret — `repr` redacts it, like everything
else in this library that holds one.

## Endpoints and regions

A bucket at Amazon is addressed virtual-hosted, `https://bucket.s3.<region>
.amazonaws.com/key`; anything else — Ceph RGW, MinIO, a site's own gateway —
is addressed path-style under the endpoint you give it:

```python
S3FileSystem("s3://my-bucket", region="eu-west-1")
S3FileSystem("s3://my-bucket", endpoint="https://rgw.example.org")
```

`$AWS_REGION` (or `$AWS_DEFAULT_REGION`) and `$AWS_ENDPOINT_URL` say the same
thing without the argument, so `xrdclient.open("s3://bucket/key")` works off the
environment alone. The signature is always SigV4, and always for the region
in force: a mismatch is what the `SignatureDoesNotMatch` from a real endpoint
usually means.

## What the bucket filesystem supports

| Operation | Request |
| --- | --- |
| `stat`, `exists`, `isdir` | `HEAD`, falling back to a one-key `ListObjectsV2` |
| `scandir`, `listdir`, `walk`, `glob` | `ListObjectsV2` with `delimiter=/`, every page |
| `read_bytes`, `open` | `GET`, with `Range` for seeks |
| `write_bytes`, `open("wb")` | `PUT`, or a multipart upload when it is long |
| `checksum` | the `ETag`, which is an MD5 |
| `remove`, `unlink` | `DELETE` |
| `rename`, `move` | `PUT` with `x-amz-copy-source`, then `DELETE` |
| `touch` | a zero-length `PUT` |
| `rmdir` | nothing, once nothing is under the prefix |
| `mkdir`, `makedirs` | nothing at all |
| `ping` | `HEAD` on the bucket |

A prefix is not a directory, so `mkdir` has nothing to do and says so by
succeeding; `rmdir` raises `BusyError` if keys are still under the prefix, and
otherwise also does nothing. Listings read a common prefix as a directory
entry, which is how `walk` and `glob` work unchanged.

`Config(s3_folder_markers=True)` makes directories real the way the S3
console does: `mkdir` writes a zero-length object named `dir/`, an empty
directory then exists (it can be `stat`-ed, listed, and seen by `walk`), and
`rmdir` deletes the marker. Markers never show up as files in a listing, and
`mkdir` over an ordinary object is refused rather than shadowed. Leave it off
against stores or buckets where a trailing-slash key would confuse other
tooling.

`checksum` returns the `ETag` only when it is a checksum: an object that
arrived as a multipart upload has a digest of digests with the part count on
the end, which is not the MD5 of anything, and that is refused rather than
handed back as though it were. `scandir(algorithm="md5")` reports the same
tag per entry, out of the listing, at no extra request.

Operations that are XRootD talking to an XRootD server about itself —
`locate`, `statvfs`, `chmod`, `query_config`, extended attributes, `prepare`,
`third_party` — raise `UnsupportedError` naming the operation. An object
store has no vocabulary for any of them.

## Writing

An object is written in one `PUT` when it fits, and as a multipart upload when
it does not: S3 has no chunked transfer encoding, so a stream longer than a
part is the only way to write without holding it all in memory.

```python
with xrdclient.open("s3://my-bucket/store/big.root", "wb") as fh:
    for block in blocks:
        fh.write(block)          # parts go up as the buffer fills
```

Parts are at least 5 MiB, the protocol minimum, whatever `config.chunk_size`
says; a larger `chunk_size` is used as-is. An upload that fails part-way is
aborted, so a bucket is not left paying for fragments of a file that never
arrived — and if the abort fails too, the original error is the one raised.

S3 reports a failed completion *inside* a `200`, which is how it can hold the
connection open while it assembles the parts; that body is read, and a failure
in it is a `ProtocolError` rather than a silent success.

## fsspec

`s3://` is deliberately *not* registered as an entry point: `s3fs` owns that
scheme, and a library that stole it would break every notebook that has it
installed. Ask for it explicitly instead:

```python
import fsspec
from xrdclient.fsspec_impl import S3XRootDFileSystem

fsspec.register_implementation("s3", S3XRootDFileSystem, clobber=True)
```

## Testing against it

`xrdclient.testing.FakeS3Server` is a bucket in the test process, with the knobs a
real one will not give you on demand — a page size, an upload that fails to
complete, an upload that is never named:

```python
from xrdclient.testing import FakeS3Server

with FakeS3Server(objects={"d/a.root": b"hello"}) as srv:
    fs = xrdclient.s3.S3FileSystem(srv.url, endpoint=srv.endpoint)
    assert fs.read_bytes("/d/a.root") == b"hello"
```

It checks signatures rather than trusting them, and the check is written out
again from the AWS specification instead of calling this library's signer, so
a client that signs the wrong string is caught rather than agreed with.

## Lower-level pieces

```python
from xrdclient.s3 import Credentials, hash_payload, sign, open_s3

headers = sign("GET", "/key?versionId=3", "bucket.s3.amazonaws.com", {},
               hash_payload(b""), credentials=creds, region="us-east-1")
```

`sign` is the SigV4 canonical request, string to sign and signing key, and
nothing else; it is verified in this library's tests against the worked
examples AWS publishes, byte for byte. `open_s3` is `open_http` for buckets,
if you want the file object without the `FileSystem` around it.
